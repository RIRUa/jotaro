# 負荷生成側のチューニングと、結果を信じるための確認

[English](tuning.md) | 日本語

負荷テストが対象を測れているのは、負荷を出すマシンがボトルネックになっておらず、数字が思ったとおりの意味を持っているときだけだ。このガイドは、負荷生成側のマシンで最初に突き当たる限界、結果のいくつかの数字が言えることと言えないこと、結果を信じる前に確認するチェックリストを扱う。ここに出てくる数字は、このガイドを書いたときの 1 台のノート PC（8 コア、macOS）での実行で得たもので、症状の形を示すためのものだ。**マシンに依存**し、ベンチマークではない。

結果の各フィールドの意味は [`result_jp.md`](result_jp.md) を見る。CI で動かす方法は [`ci_jp.md`](ci_jp.md)、負荷を複数のマシンに分ける方法は [`multi-machine_jp.md`](multi-machine_jp.md) にある。

## 負荷生成側マシンの限界

負荷生成側で最初に起きる問題は、ファイルディスクリプタ、エフェメラルポート、CPU の 3 つだ。最初の 2 つはエラーとして現れ、今のところ `other` に入る（分類することは [#110](https://github.com/RIRUa/jotaro/issues/110) で求められている）。これらに当たった実行は、対象について何も語らない。

### ファイルディスクリプタ

同時に開いている接続はどれも負荷生成側のファイルディスクリプタを 1 つ使い、HTTP/1.1 では、処理中のリクエストごとに専用の接続が要る。オープンモデルで同時に動くイテレーション数は `Plan.MaxUsers` で上限が決まり、これは**既定で 1 000**（0 は 1 000 の意味）で、各イテレーションは処理中のリクエストを持ちうる（`Step.Parallel` ならもっと多い）。同時数は、ほぼレートにイテレーション 1 回の時間を掛けたものだ（毎秒 3 000 回の到着が 400 ms ずつなら同時に 1 200 で、既定の上限ではまず到着が取りこぼされる）。クローズドモデルでは、ほぼ `Users` と同じ数の接続になる。ほかに、プロセス自身が少しディスクリプタを使う（標準入出力、`Plan.Raw` のファイル、`MetricsAddr` のリスナー）。

大事なのは**ハード**リミットだ。Go のプログラムは、Unix では起動時に、開けるファイル数のソフトリミットをハードリミット（マイナス 1。macOS では最大でも `kern.maxfilesperproc`）まで引き上げる（Go 1.19 以降。jotaro は Go 1.25 が必要）ので、よくある 1 024 というソフトリミットだけで困ることはない。プロセスが実際に持てる数を確かめる。

```sh
ulimit -Hn          # ハードリミット。Go のプログラムの上限はこれ
ulimit -n 65536     # このシェルとその子プロセスで引き上げる（ハードリミットを上げるには権限が要る）
```

どこから来た制限かで、上げ方が決まる。テストを起動するシェルの `ulimit`、systemd のユニットの `LimitNOFILE=`、`docker run` の `--ulimit nofile=65536:65536`、Kubernetes ではコンテナランタイムの設定だ。ハードリミットが低くなりがちなのは、コンテナや CI のイメージだ。

**症状。** 実行が `errors: other=N` を大きな N で報告し、2xx がほとんど、または全く出ない。プロセスを制限（`ulimit -Sn 128; ulimit -Hn 128`）して、ローカルのサーバーに 200 ユーザーで 4 秒間負荷をかけて再現した結果:

```
requests:   934323 (232409.79/s)
status:     2xx=24032
errors:     other=910291
conns:      new=124 reused=23908 (99.5% reused)
```

「リクエスト」の 97% はソケットを作れずに即座に失敗した。クローズドモデルのユーザーはリクエストが即座に失敗すると次を全速力で送る（[#99](https://github.com/RIRUa/jotaro/issues/99)）ので、これだけ件数が多くなる。今のところ `other` は（受け皿の種類なので）対象によるリセットと区別できない。だから環境のほうを見る。`ulimit -Hn` を、計画した同時数と突き合わせ、実行中にプロセスが持っているディスクリプタの数を数える（Linux では `ls /proc/<pid>/fd | wc -l`、ほかでは `lsof -p <pid> | wc -l`）。

### エフェメラルポートと TIME_WAIT

1 つのアドレスとポートへの接続は、どれもローカルの（エフェメラル）ポートを 1 つ使い、閉じた接続は、先に閉じたほうの側が、しばらく（Linux では 60 秒）そのポートを `TIME_WAIT` のまま持つ。Linux の既定では `net.ipv4.ip_local_port_range` が 32768〜60999 で、約 28 000 ポートだ。つまり 1 つのアドレスに**新しい接続**を、おおよそ 28 000 / 60 秒、毎秒約 470 より速く開く負荷生成側は、ポートが尽きる。既定の範囲はシステムによって違うことがある。`sysctl net.ipv4.ip_local_port_range` で読み、`TIME_WAIT` のソケット数は `ss -s`（Linux）または `netstat -an | grep -c TIME_WAIT` で数える。

普通の実行では起きない。jotaro が接続を再利用するからだ。すべてのユーザーが 1 つの `http.Transport` を共有し、レスポンスボディは最後まで読むので、接続は再利用できる状態に保たれる。このガイドのための実行では再利用率は 99% 以上だった（200 ユーザーで `conns: new=200 reused=38720 (99.5% reused)`）。起きるのは、再利用が壊れたときだ。

- 対象、またはその手前のプロキシが、レスポンスのたびに接続を閉じる（`Connection: close`、HTTP/1.0、ごく短い keep-alive タイムアウト）。`TIME_WAIT` は主に先に閉じる側、つまり対象に残るが、どのリクエストも、ハンドシェイクを伴う新しい接続を張ることに変わりはない。
- トランスポートがアイドルで保つ数より多くの接続が要るバースト（既定のトランスポートが保つアイドル接続は最大 100、ホストごとに 2）。余った接続は負荷生成側が閉じる。負荷生成側自身が `TIME_WAIT` を抱えてポートが尽きるのは、このケースだ。

**症状。** レポートの `conns:` 行の再利用率が低く、`connect:`（と `dns:`、`tls:`）の行の観測数がほぼリクエスト数と同じになる。各リクエストが接続を張ったからだ。実行を終わらせるエラーは `connect: cannot assign requested address` で、今は `other` に数えられる。原因を直す。対象側で keep-alive を効かせる、負荷を対象のより多くのアドレスに散らす、負荷生成側のポート範囲を広げる、または複数の負荷生成側を使う（各自のポートを持つ。[`multi-machine_jp.md`](multi-machine_jp.md) を参照）。

### CPU と GOMAXPROCS とコンテナ

レポートには `loadgen:` 行（たとえば `cpu max 5.2% (avg 5.1%), goroutines max 602`）があり、どれかの秒の CPU の最大値が **90%** に達すると、テキストと HTML のレポートに警告が出る。負荷生成側自身がボトルネックかもしれず、測った latency が対象の本当の振る舞いより悪く見える、という警告だ。この割合は、その秒にプロセスが使った CPU 時間を、経過時間と `GOMAXPROCS` で割ったもので、100% は Go のランタイムが使うのを許された CPU 全部を意味する。測れないとき（今は Windows、[#95](https://github.com/RIRUa/jotaro/issues/95)）は -1 で、`cpu n/a` と出る。`jotaro check` はこれを判定できないので、警告は自分で読む（[`ci_jp.md`](ci_jp.md) のワークフローは、これをアノテーションにしている）。

- **どれだけかかるか。** 単純なリクエストなら少ない。20 ms で答えるローカルのサーバーに 200 ユーザーで負荷をかけた実行は、8 コアの `cpu max 5.2%`、つまり約 0.4 コア分で毎秒約 9 700 リクエストを送った（サーバーは別のプロセス）。JSON のデコード、大きなボディ（レスポンスはすべてメモリに全部読み込まれる。[#100](https://github.com/RIRUa/jotaro/issues/100)）、シナリオのコードは、もっとかかる。だから自分のシナリオで測る。負荷を段階的に上げ、`loadgen:` を見る。リクエストごとの負荷生成側自身のコストと、そのベンチマークの方法は [`performance_jp.md`](performance_jp.md) にある。
- **`GOMAXPROCS` とコンテナ。** CPU の割合は `GOMAXPROCS` に対するものなので、その数は、マシンが実際にくれる量でなければならない。Go 1.25 以降では、`go.mod` の `go` 行が 1.25 以上なら（jotaro は 1.25 を要求するので、あなたのもそうだ）、ランタイムはコンテナ（cgroup）の CPU 制限からも `GOMAXPROCS` を決め、その値を更新し続ける。古いランタイムはホストのコア数を使う。64 コアのホストで CPU 2 つに制限されたコンテナでは、そのようなプロセスは 64 スレッドを 2 CPU のクォータに対して走らせ、スロットリングされ、飽和しているのに CPU が数% と読める。`GOMAXPROCS` を自分で設定する（環境変数）と上書きできる。ランタイムが CPU 制限を見ないときは、CPU 制限と同じ値にする。
- **熱くなったとき**: レートやユーザー数を下げる、負荷生成側にコアを増やす、または複数の負荷生成側に負荷を分ける（[`multi-machine_jp.md`](multi-machine_jp.md)）。警告が出た実行の latency は信じない。

### 負荷生成側と対象を同じマシンに置く

サンプルは、ほかに何も用意しなくても動くように、同じプロセスの中でモックサーバーを起動する。本物のテストはそうしてはいけないし、1 台での実行はスモークテストであって、容量の測定ではない。

- CPU を共有するので、対象と負荷生成側は互いを遅くする。同じプロセスで対象が動くとき（`examples/checkout` のように）は、負荷生成側の CPU の数字に対象の分も含まれる。
- トラフィックはループバックインターフェースを通る。ネットワークの遅延も、パケットロスも、帯域の制限もないので、ほかの場所のクライアントが見るより latency は低くなり、飽和したネットワークが結果に入ることはない。
- 両方のソケット、メモリ、`TIME_WAIT` のエントリは 1 つのカーネルから出るので、上の限界により早く達する。

負荷生成側は専用のマシンに置き、ネットワーク上で対象の近くか、モデル化したい距離に置く。1 つのランナーで両方を動かす CI ジョブは、同じ構成の実行どうしを比べるなら妥当な回帰テストで（[`ci_jp.md`](ci_jp.md) を参照）、それ以上のものではない。

## 数字の意味

### `corrected` と `latency`

`latency` は、リクエストを送ってからレスポンスを読み終えるまでの時間だ。`corrected` は**予定された**開始時刻からの時間で、クローズドモデルでは 2 つは等しい。オープンモデル（`Arrival`）では、イテレーションの最初のリクエストだけが予定された到着時刻を受け取り、そのイテレーションの後のリクエストでは `corrected` は `latency` と等しい。だから 2 つの差は、予定された到着から最初のリクエストが送られるまでに過ぎた時間だ。

今の実装では、到着は決してキューに入らない。すでに `MaxUsers` 個のイテレーションが動いているときは、到着は遅らされずに取りこぼされて数えられる（`dropped`）。だから追いつけない対象は **`dropped`** と、増える並行数として現れ、走れたイテレーションの `corrected` は `latency` に近いままだ。20 ms の対象、毎秒 2 000 回の到着、`MaxUsers: 20` で再現した結果: `latency` の p50 は 20.0 ms、`corrected` の p50 は 20.4 ms、`dropped` は 4 252（到着のおよそ半分）。2 つの間に差を作るのは、負荷生成側かシナリオの側にある。ディスパッチャを起こすタイマー、ゴルーチンの起動、ユーザーの作成（到着ごとに Cookie jar と HTTP クライアント）、飽和した CPU やガベージコレクション、そしてシナリオが最初のリクエストの前に行う処理や `Think` だ。

**負荷生成側自身の下限。** どこにもキューが無くても、`corrected` は `latency` より、負荷生成側が加える一定量だけ大きい。[#119](https://github.com/RIRUa/jotaro/issues/119) は、アイドルの 4 コアの Linux マシンで、毎秒 100〜5 000 回の到着のとき 0.5〜1 ms と測った（毎秒 100 回では `latency` の p50 が 266 µs、`corrected` の p50 が 918 µs）。このガイドに使ったノート PC では、20 ms の対象に毎秒 100 回、取りこぼしなしの実行で、`latency` の p50 が 20.8 ms、`corrected` の p50 が 22.09 ms、つまり 1.3 ms 多かった。原因はおそらくディスパッチャのタイマーの粒度で、直し方（`schedule_delay` として別に測る、早めに起きる）はまだ未解決だ。それまでは:

- この下限のせいで、速い対象が満たせない `corrected_*` のしきい値を置かない（`corrected_p95<1ms` はどんな対象も満たせない）。
- `corrected` と `latency` の約 1 ミリ秒の差を、対象の性質として読まない。数十ミリ秒の差や、0 を超える `dropped` はしるしだ。

### HTTP/2 の接続共有

すべての仮想ユーザーは 1 つの `http.Transport` を共有する。HTTP/1.1 では、処理中のリクエストごとにほぼ 1 接続になる。HTTP/2 を提供する対象への HTTPS では、Go は HTTP/2 をネゴシエートし（複製した既定のトランスポートは `ForceAttemptHTTP2` が有効）、**全ユーザーを 1 つの接続に多重化**する。ローカルの TLS サーバーに 50 ユーザーで 2 秒間負荷をかけて測った結果:

| | HTTP/1.1 | HTTP/2 |
|---|---|---|
| レポートの `conns:` | `new=50 reused=4728` | `new=1 reused=4754` |
| サーバーが受け付けた接続 | 50 | 49〜50。ほとんどは、使われずに閉じられた開始時の接続 |

テストにとっての意味（[#112](https://github.com/RIRUa/jotaro/issues/112)）: 1 000 の「ユーザー」は 1 つのクライアントだ。接続をバックエンドに固定するロードバランサーは、全員を 1 つのインスタンスに送る。パケットを 1 つ失うと全ストリームが同時に止まる。サーバーの接続ごとの制限（`MAX_CONCURRENT_STREAMS`、接続ごとのレート制限）はテスト全体を絞る。`conn_new` と TLS の時間は 1 回のハンドシェイクを表し、ユーザーの接続コストではない。サーバーが受け付ける接続も、`conn_new` よりずっと多いことがある。`net/http` が開始時に余分に張って使わずに閉じる接続は数えないからだ（[#184](https://github.com/RIRUa/jotaro/issues/184)）。

結果にプロトコルは記録されないので、数字と並べて書いておく。`conns:` 行（HTTPS なのに `new` がユーザー数よりずっと少ない）とサーバーから分かる。処理中のリクエストごとに 1 接続に戻すには、`Run` の前に `http.DefaultTransport` の HTTP/2 を切る。`Run` はそれを複製する。これはプロセス全体のトランスポートを変えるが、テストだけを動かすプログラムでは問題ない。そしてこの複製に頼っている（本来の置き場所は `Plan.Transport` だ。[#89](https://github.com/RIRUa/jotaro/issues/89)）。

```go
package main

import (
	"crypto/tls"
	"net/http"
)

// forceHTTP1 は、このプロセスの実行で HTTP/2 を切る。jotaro.Run の前に呼ぶ。
func forceHTTP1() {
	t, ok := http.DefaultTransport.(*http.Transport)
	if !ok {
		return // 既定のトランスポートが差し替えられている: 変えるものがない
	}
	t.ForceAttemptHTTP2 = false
	t.TLSNextProto = map[string]func(string, *tls.Conn) http.RoundTripper{}
}

func main() { forceHTTP1() }
```

これを入れると、上と同じ実行は `new=50 reused=4600` になり、サーバーには HTTP/2 のリクエストが 1 つも来なかった。

### `bytes_in` と `bytes_out`

`bytes_in` は、`net/http` が展開した**あとの**レスポンスボディの長さだ。トランスポートは自分で gzip を要求し、シナリオがボディを見る前にエンコーディングを外す。`bytes_out` はリクエストボディの長さで、リクエスト行とヘッダーは数えず、レスポンスヘッダーも数えない。ワイヤ上のトラフィックではない（[#114](https://github.com/RIRUa/jotaro/issues/114)）。ここで測った結果: gzip で符号化した 100 000 バイトのテキストを返すハンドラ（ワイヤ上は 183 バイト）では、2 461 リクエストで `bytes: in 234.7MB` になった。2 461 × 100 000 バイト（234.7 MiB）だ。228 文字の bearer トークンをヘッダーに載せたリクエストでも `out 0B` だった。

使うのは、シナリオが扱ったものの大きさを実行どうしで比べるためで、回線やエグレスの上限を判断するためではない。帯域は、負荷生成側と対象のネットワークインターフェースのカウンター（または監視）を読む。

## 結果を信じる前に

次のリストは、MCP リソース `jotaro://result` が「Reading a result」の下で出しているもの（[`internal/mcpserver/content/result.md`](../internal/mcpserver/content/result.md)）と同じ内容で、アシスタントと人が同じものを読むようにしてある。8〜12 は、負荷生成側のためにここで足した。順に確かめる。最初の 2 つが、ほかの数字を信じてよいかどうかを決める。

<!-- 1〜7 は internal/mcpserver/content/result.md（"Reading a result"）からの翻訳。内容を揃えておくこと。 -->

1. **テストは対象を測れたか。** 負荷生成側の CPU が 90% 以上に達したなら、負荷生成側自身がボトルネックで、latency は実際より悪く見える。負荷を下げるか、複数のマシンに分けて、結果を `jotaro merge` でまとめる。
2. **計画した負荷はかかったか。** `dropped > 0` は、新しい到着の時刻になったとき、すでに `MaxUsers` 個のイテレーションが動いていたことを意味し、計画より少ないシナリオしか始まっていない。対象がレートに追いつけなかった（または `MaxUsers` がシナリオの長さに対して低すぎる）。
3. **エラー。** 率だけでなく種類を見る。`timeout` と `connection_refused` は、対象が過負荷か停止していることを指す。リクエストのエラーは、間違った応答については何も言わない。`failed` が 0 より大きいのにリクエストのエラーがないステップや、`status` に `4xx` / `5xx` があるのは、対象がシナリオの受け入れない応答を返したことを意味する（`Expect*` のチェックが失敗した、`expect_mismatch`）。`status` で `5xx`（サーバーの失敗）や `4xx`（シナリオが間違ったものを送っている。たとえばトークンがない）を確かめる。失敗したステップがないのに `4xx` や `5xx` があるなら、それは `Expect*` でチェックしていないリクエストのものだ。間違った応答をしきい値で落とすには、シナリオがステップのエラーを返すようにして、`iteration_fail_rate` で判定する。
4. **ステップごとの latency。** ステップを比べて、遅いものを見つける。平均より p95 と p99 を優先し、`max` を p99 と比べて、まれな停止を見つける。
5. **オープンモデル: `corrected` と `latency`、そして `dropped`。** この 2 つは別のものを示す。`MaxUsers` が埋まっているところに来た到着は、遅らされずに取りこぼされるので、追いつけない対象は `dropped > 0`（項目 2）として現れ、走れたイテレーションの `corrected` は `latency` に近いままだ。差が小さくても対象が健全だとは言えないので、まず `dropped` を見る。`corrected` が `latency` よりずっと大きい（数十ミリ秒、または数倍）なら、イテレーションが予定より遅く始まったので、ユーザーはリクエストごとの latency が示すより長く待つことになる。この遅れの原因は、遅い対象ではなく、負荷生成側かシナリオにある。ディスパッチャが遅く起きた（飽和した CPU、ガベージコレクション）か、シナリオが最初のリクエストの前に使う時間（`Think`、ほかの処理）だ。アイドルのマシンで約 1 ミリ秒の差は、負荷生成側自身の下限だ。オープンモデルは `corrected_p95` などで、`dropped<1` と併せて判定する。
6. **接続。** `dns` / `connect` / `tls` の観測数が多いなら、接続が再利用されておらず、その確立時間が `latency` に含まれている。
7. **時間の経過。** `summarize_result` の最悪の秒や、HTML レポートのグラフは、実行が進むにつれて悪化したのか（latency が増えた）、ある時点だけ遅かったのかを示す。
8. **負荷生成側の環境のエラー。** 応答が少ないのに `other` のエラーが多いなら、それは対象ではなく負荷生成側の限界で、ファイルディスクリプタの上限かエフェメラルポートだ（[上](#負荷生成側マシンの限界)を参照）。[#110](https://github.com/RIRUa/jotaro/issues/110) がそれらを分類するまでは、`other` はどちら側の失敗かを言えない。
9. **`corrected` の下限。** 項目 5 は [`corrected` と `latency`](#corrected-と-latency) と合わせて読む。この実装では、`MaxUsers` が埋まっているところに来た到着は取りこぼされるので、遅い対象は `dropped`（項目 2）として現れ、約 1 ミリ秒の差は負荷生成側自身のものだ。
10. **HTTPS: 接続は 1 つか、たくさんか。** `conn_new` がユーザー数よりずっと少ない、または TLS ハンドシェイクが 1 回だけなら、HTTP/2 が全ユーザーを 1 つの接続で運んだということだ（[HTTP/2 の接続共有](#http2-の接続共有)）。結果は、どのプロトコルが動いたかを言わない。
11. **負荷生成側はどこで動いたか。** 対象と同じマシンやランナーなら、CPU、ネットワーク、ソケットが共有され、トラフィックはループバックだ（[同じマシン](#負荷生成側と対象を同じマシンに置く)）。数字と並べてそう書く。
12. **リクエストは十分か。** 100 件に満たないと p99 は一番遅い 1 件にすぎず、20 件に満たないと p95 もそうなる。`summarize_result` はこれを警告する。`jotaro check` や CLI では、`requests` を自分で数える。

MCP のツール `summarize_result` は、この計算の一部を代わりに行い、`warnings` を返す。同じリソースの「Warnings of `summarize_result`」を見る。項目 8〜11 は扱わない。
