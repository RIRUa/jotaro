# ジェネレーターの性能

[English](performance.md) | 日本語

1 台のジェネレーター（jotaro を動かす 1 プロセス）がどれだけの負荷を出せるか、それをどう測っているか、悪化しないようにどう守っているかをまとめる。ここにある数字は 1 台のマシンと 1 つの Go バージョンでの値で、桁と傾向を示すだけで保証ではない。台数を決める前に、自分のマシンで測ること。

## 何を測っているか

ベンチマークは `bench_test.go` にある。共有ランナーでは時間が安定しないので、CI では実行しない。

```sh
go test -run='^$' -bench='Iteration|NetHTTPFloor|RunEndToEnd' -benchmem -count=10 .
```

| ベンチマーク | 動かすもの |
| --- | --- |
| `BenchmarkIteration` | クエリ 1 つと Bearer ヘッダー付きの `GET` を 1 回行う反復 1 回分。`newUser` → `Scenario.run` → `User.Step` → リクエストビルダー → `executor.do` → コレクターと集計まで通す。トランスポートは固定の `200` を返すスタブなのでネットワークも `net/http` のトランスポートのコストもなく、残るのはジェネレーター自身の分と `http.Client` のコスト。 |
| `BenchmarkIterationPostJSON` | 同じものを `POST` と JSON ボディで行う。 |
| `BenchmarkIterationFiveSteps` | 1 反復に 1 リクエストずつの 5 ステップ。反復ごとに 1 回払うコストとリクエストごとに払うコストを切り分ける。 |
| `BenchmarkIterationOpenModel` | オープンモデルが到着ごとに行うのと同じく、予定到着時刻を設定した `BenchmarkIteration`。 |
| `BenchmarkNetHTTPFloor` | 同じリクエストを `net/http` だけ（リクエスト・クライアント・`io.ReadAll`）で同じスタブへ送る。上の各ベンチがこれを上回った分が jotaro の取り分。 |
| `BenchmarkRunEndToEnd` | 同じプロセス内の `httptest` サーバーに、16 ユーザーで 1 秒間のクローズドモデルの `Run` を丸ごと行う。`req/s` と `req/s/core`（`GOMAXPROCS` あたり）を報告する。 |

## 実測した上限の目安

Apple M3（8 コア）、Go 1.27、他の処理が動いている状態での値。

| | #141 より前 | #141 より後 |
| --- | --- | --- |
| `GET` 1 回の反復（スタブ） | 約 3.4 µs・6.7 KB・91 回のアロケーション | 約 3.1 µs・5.7 KB・65 回 |
| JSON ボディの `POST` 1 回 | 約 4.2 µs・6.5 KB・99 回 | 約 3.7 µs・5.6 KB・76 回 |
| 1 反復に 5 ステップ | 約 16.6 µs・31 KB・407 回 | 約 14.5 µs・27 KB・321 回 |
| 同じリクエストを `net/http` だけで | 約 2〜4 µs・4.0 KB・38 回 | （同じ） |

つまり jotaro と `http.Client` を合わせて、1 リクエストあたり数マイクロ秒の CPU と約 65 回のアロケーションが必要になる（うち `net/http` だけで 38 回なので、jotaro 自身の分は約 27 回）。ネットワークを除けば 1 コアあたり毎秒 30 万件強に相当する。実際の限界は、ネットワーク・対象・`net/http` のトランスポートにある。`BenchmarkRunEndToEnd` は、サーバーを同じプロセスに置いた状態（サーバーの CPU も含む）で、そのマシンでは 1 コアあたり毎秒およそ 7 000〜11 000 件だった。実ネットワーク、TLS、大きなボディでは低くなると見込むこと。台数を増やすのは、このファイルの数字に達したときではなく、ヘルス警告（CPU 90% 超）や `corrected` と `latency` の差がジェネレーターの限界を示したとき。

ジェネレーター側の 1 リクエストあたりのコストは対象に依存しない。毎秒 20 000 リクエストなら、jotaro と `http.Client` のアロケーションは毎秒約 130 万回・110 MB/s になり、従来の 180 万回・135 MB/s から減った。

## 何をして、何を残したか

ジェネレーター側の経路（jotaro と `http.Client`）のアロケーションを、1 リクエストあたり 91 回から 65 回に減らした（#141）。

- エラー種別の判定（`classify`）は、エラーがないとき（成功したステップと反復のすべて）、`errors.As` の対象を確保する前に戻る。
- リクエストの `httptrace.ClientTrace` を、トレーサーと同じアロケーションに置く。
- `User`・その `http.Client`・クッキージャーを 1 回のアロケーションにまとめ、ジャー自体は最初の `Set-Cookie` で作る（クッキーを一度も受け取らない反復ではジャーを確保しない）。
- `Step` とその executor を 1 回のアロケーションにまとめ、executor はステップごとにメソッド値を作らず、コレクターへ直接記録を渡す。
- ボディのないリクエストは `net/http` にボディのリーダーを渡さない。レスポンスボディは `Content-Length` から決めたバッファに読み込む（1 MiB まで。それより長い・長さ不明のときは従来どおり伸ばす）。

そのままにしたもの：送信リクエストの `Header.Clone()`（クッキージャーは渡されたリクエストに `Cookie` ヘッダーを足すので、1 度組んだリクエストを 2 回送ったときにビルダーのヘッダーが変わってはいけない）、反復ごとの `http.Client`（`User.Client` は反復ごとに自前のクッキージャーを持つと説明していて、プログラムが保持することもある）、トレースの 8 個のフック（フックは状態が要るのでそれぞれクロージャーになる。リクエストが戻った後でも `net/http` がフックを呼ぶことがあるので、プールは安全でない）。レスポンスボディの制限・破棄は #100、オープンモデルの到着ごとの準備は #119 で扱う。

## ガード

`TestIterationAllocations`（`alloc_test.go`）は、上の 3 つのシナリオをスタブに対して動かし、1 反復のアロケーションが余裕のある上限を超えたら失敗する。数えるのは時間ではなくアロケーションなので結果は決まっていて、CI でも動く。`-race` ではアロケーション数が変わるので、そのときはスキップする。そのため CI では、すべてのテストセルで `-race` なしの専用ステップとして実行する。正当な変更の後で失敗したら、ベンチマークで測り直し、上限を引き上げて、その理由をプルリクエストに書くこと。
